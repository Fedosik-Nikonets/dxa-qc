# Оценка качества денситометрических исследований (DXA)

Сервис принимает рентгеновское денситометрическое исследование в формате
DICOM и оценивает качество его выполнения по критериям ТЗ раздела 2.3:
определяет анатомическую область, проверяет её правилами качества и
выдаёт таблицу, в которой для каждого файла указан класс качества и, при
нарушении, его тип.

Ключевое свойство решения: **все правила детерминированы и объяснимы**.
Три из пяти считаются из маски кости геометрией, артефакты — одним
физическим признаком с обученным порогом (веса 1650 байт), ротация бедра —
двумя порогами по профилю медиального края кости (границы в json на 1.2 КБ).
Ни torch, ни scikit-learn на инференсе не нужны. Каждый шаг можно показать
на слайде и защитить на разборе, а overlay-серия показывает его на каждом
снимке.

> **Публичная копия.** Снимок тега `v1.1.0` рабочего репозитория одним
> коммитом, без истории. Код, веса, таблицы, отчёты и документация — как в
> теге; образ `dxa-qc_1.1.0.tar.gz` собран из этих же `src/`, `models/`,
> `docker/`. Убрано то, что принадлежит организатору или показывает снимки
> обучающего набора: `Data/` (исследования и разметка), `Task/` (ТЗ),
> PNG-листы с фрагментами снимков в `reports/`, картинки слайдов в
> `presentation/src/assets/`, инструменты разметки `annotations/*.html`,
> `*.pdf` и файл `presentation/DXA_QC_presentation.pptx` (PDF презентации —
> по ссылке из формы сдачи). Листы пересобираются скриптами из
> `docs/training.md`, если положить набор организатора в `Data/`.

## Быстрый старт: контейнер

Нужен только Docker (Linux или macOS). Решение работает без сети:
правила и веса лежат в образе, пакетный прогон запускается с
`--network none` (ТЗ 3.2).

```bash
./build.sh                                   # сборка образа dxa-qc:1.1.0 и проверка без сети
./run.sh <каталог или zip> <каталог результатов>
```

В каталоге результатов — `result.xlsx` (таблица ТЗ 2.5 и балл нарушения
`quality_score`), `overlays.zip` (дополнительная серия и отчёт DICOM SR на
исследование, ТЗ 2.6–2.7) и `diagnostics.csv`. На вход годится и
архив организатора как есть (`НД_для_обучения.zip`): имена в cp866
читаются правильно, обёртка `Исследования/` снимается автоматически.

Для машины проверки (x86_64) образ собирается и сохраняется в файл так:
`PLATFORM=linux/amd64 ./build.sh --save` → `dxa-qc_1.1.0.tar.gz`, на
месте — `docker load < dxa-qc_1.1.0.tar.gz`.

Состав образа: `python:3.12.7-slim-bookworm`, зависимости из
`docker/requirements-runtime.txt` — все версии закреплены, включая
транзитивные, ставятся только из готовых колёс, `pip check` при сборке.
torch и прочие библиотеки обучения в образ не входят: на инференсе они не
нужны, и это проверяется при сборке. Процесс в контейнере — не root.

### Системные требования (ТЗ 3.1)

GPU не нужен и не используется: решение — геометрия, один физический
признак и два порога. Весь обучающий набор (100 исследований, 499 файлов):
без overlay — 7 с и 225 МБ пиковой памяти процесса, с overlay-серией в PNG
и DICOM — 30 с и 242 МБ (Linux-VM на MacBook Air M2, 24 сентября; ранее на
облачной машине с 2 vCPU: 10 с без overlay). Архив overlay пишется потоком,
поэтому память от размера набора почти не зависит. Самое долгое
исследование стресс-теста (кадр 2048×2048) — 0.6 с при лимите 3 минуты.

| | минимум | рекомендуется |
|---|---|---|
| процессор | 1 ядро x86_64 или arm64 | 2 ядра и больше |
| память | 1 ГБ | 2 ГБ |
| диск | образ + входные данные + ~0.3 МБ на снимок под overlay-серию (PNG и DICOM; только PNG — 0.1 МБ) | то же |
| GPU | не нужен | не нужен |
| ПО | Docker 20+ | Docker 24+ |

## HTTP API

`./run.sh --serve` поднимает сервис на `http://localhost:8000`: по корневому
адресу — веб-интерфейс (ниже), интерактивная документация API — `/docs`.

| метод | путь | вход | выход |
|---|---|---|---|
| GET | `/health` | — | статус, версия, какие модели загружены (артефакты, ротация, балл) и их sha256 |
| POST | `/batch` | zip-архив с исследованиями (поле `file`); параметры `format=xlsx\|csv`, `overlays=true\|false`, `overlay_format=both\|dicom\|png`, `region_lang=ru\|code` | файл таблицы; с `overlays=true` — zip с `result.<format>` и `overlays.zip` |
| POST | `/predict` | файлы одного исследования (поле `files`: DICOM или zip), параметр `study` | JSON: строки таблицы, итоговый `quality_class` и `quality_score` исследования |
| GET | `/` | — | веб-интерфейс |
| POST | `/ui/jobs` | zip или DICOM-файлы одного исследования (поле `files`); `overlays=true\|false` | JSON задания: строки таблицы, сводка, список файлов |
| GET | `/ui/jobs/{job}/files/{name}` | `result.xlsx`, `result.csv`, `overlays.zip` | файл задания |
| GET | `/ui/jobs/{job}/overlay` | `path` — `path_to_study`, `kind=png\|dcm` | overlay одного файла: PNG или DICOM Secondary Capture |

```bash
curl -F file=@НД_для_обучения.zip "http://localhost:8000/batch?overlays=true" -o result.zip
curl -F files=@CR000000.dcm -F files=@CR000001.dcm "http://localhost:8000/predict?study=S1"
```

Ошибки входа — ответ 400 с текстом причины (не архив, небезопасные пути в
архиве, превышен размер), ошибки параметров — 422. Ошибка на отдельном
файле ответа не ломает: как и в CLI, это строка `Failure` в таблице. API
— тонкая оболочка над тем же `batch.run`, что и командная строка: таблицы
совпадают построчно (тест `test_service.py`).

### Веб-интерфейс (ТЗ 2.6)

Открыть `http://localhost:8000/` после `./run.sh --serve`. Загрузка zip-архива
с исследованиями (хоть весь набор организатора) или DICOM-файлов одного
исследования перетаскиванием → пакетная обработка тем же конвейером, что у
CLI и `/batch` → на странице:

* сводка: исследования, файлы, сколько исследований и изображений с
  нарушениями, ошибки чтения, время на исследование;
* таблица по исследованиям с вердиктом исследования, фильтрами «с
  нарушениями / норма / ошибки чтения», по типу нарушения и поиском;
* просмотр overlay выбранного снимка с расшифровкой нарушений и
  скачиванием его DICOM Secondary Capture;
* скачивание `result.xlsx`, `result.csv` и `overlays.zip`.

Страница — один файл `src/dxa_qc/web/index.html` без внешних ресурсов:
работает в контейнере без сети. Данные из архивов выводятся только как
текст (никакого `innerHTML`). Входные файлы удаляются сразу после
обработки, хранятся результаты пяти последних заданий (каталог —
`DXA_QC_JOBS`, по умолчанию во временной папке). Светлая и тёмная тема,
вёрстка работает и на экране телефона.

## Запуск без контейнера

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
pip install -e . --no-deps          # чтобы работала команда ниже без PYTHONPATH

python -m dxa_qc.batch --input <каталог или zip> --output result.xlsx
python -m dxa_qc.service --port 8000            # API
```

Без установки пакета то же самое запускается как
`PYTHONPATH=src python -m dxa_qc.batch ...`.

Полезные ключи:

| ключ | что делает |
|---|---|
| `--diagnostics FILE.csv` | служебные колонки (углы, отступы, пороги) для разбора ошибок |
| `--overlays FILE.zip` | overlay-серия (ТЗ 2.6, 2.7) на каждый файл: DICOM Secondary Capture в исследовании исходника и PNG |
| `--overlay-format dicom\|png\|both` | что класть в архив overlay (по умолчанию `both`) |
| `--region-lang code` | короткие коды областей вместо русских названий |
| `--limit N` | обработать только первые N файлов |
| `--quiet` | без прогресса в stderr |

Выход — `.xlsx` или `.csv` по расширению. Запись детерминирована: два
прогона на одних данных дают побайтово одинаковый файл, кроме колонки
времени обработки.

## Выходная таблица

Восемь колонок ТЗ 2.5 в требуемом порядке:
`path_to_study`, `study_uid`, `image_uid`, `anatomical_region`,
`quality_class`, `violation_type`, `processing_status`,
`time_of_processing`. После них — три колонки, которых в ТЗ 2.5 нет, поэтому
позиционный разбор первых восьми не ломается:

* `quality_score` — балл нарушения в [0, 1] для ROC-AUC (подробности ниже);
* `study` — идентификатор исследования (имя каталога);
* `projection` — проекция снимка (ТЗ 2.2: «определение анатомической
  области **и проекции**»). Берётся из тега ViewPosition (0018,5101), а
  если его нет — прямая по протоколу денситометрии поясничного отдела и
  бедра (у GE Lunar — «AP Spine», «Femur»). В обучающем наборе тега нет ни
  в одном из 499 файлов, поэтому везде `прямая (AP)`; источник значения —
  в диагностике, `projection_source=tag|protocol`. Боковая проекция по тегу
  помечается как `боковая (LAT)`: правила рассчитаны на прямую.

Решения по формату, которых в ТЗ нет:

* **строка на каждый файл**, а не на уникальный кадр: половина файлов
  набора — точные копии, но выбрасывать их из таблицы значит терять
  соответствие с входом. Дедупликация есть, но только внутри конвейера:
  область и предсказание считаются один раз на уникальный кадр;
* **у `Failure` колонка `quality_class` пуста**, а не равна нулю. Ноль
  означал бы «снимок качественный» — утверждение о файле, который не
  удалось прочитать. Текст ошибки идёт в `violation_type`;
* **строка появляется даже на не-DICOM файл**: молча пропускать опаснее;
* **`quality_score` — балл нарушения в [0, 1]**, девятая колонка. ТЗ 8.4
  называет ROC-AUC приоритетной метрикой, а по бинарному `quality_class` она
  вырождается в сбалансированную точность. Балл — вероятность хотя бы одного
  нарушения среди правил области (noisy-OR), у каждого правила
  `sigmoid(a·маржа)`, где маржа — насколько измерение за порогом, а крутизна
  `a` подогнана по разметке (`models/quality_score_v1.json`,
  `scripts/26_quality_score.py`). Балл **больше 0.5 тогда и только тогда,
  когда `quality_class = 1`** — решения он не меняет. У `Failure` пуст;
* **имя области — по-русски словами ТЗ 2.3**. Единого словаря нет ни в ТЗ,
  ни в разметке; русское название читается человеком без словаря.

Ни один входной файл не может уронить обработку остальных (ТЗ 2.7): любая
ошибка даёт строку со статусом `Failure` и текстом причины.

## Overlay-серия

С ключом `--overlays overlays.zip` рядом с таблицей пишется zip-архив
(ТЗ 2.7: «zip-архив с дополнительными сериями»). На каждый входной файл в
нём два представления одной картинки:

* **`<path_to_study>.overlay.dcm` — DICOM Secondary Capture** (ТЗ 2.6:
  «дополнительная серия»). Объект ложится в **то же исследование**
  (StudyInstanceUID и атрибуты пациента — из исходника), отдельной серией
  `DXA QC overlay` (номер 9001) по серии на исследование; ссылка на исходный
  снимок — SourceImageSequence, вердикт — в ImageComments. Открывается в
  любом DICOM-просмотрщике и загружается в PACS рядом с оригиналом. RGB без
  сжатия, Explicit VR Little Endian; подписи вшиты в пиксели
  (`BurnedInAnnotation=YES`). UID выводятся из исходных детерминированно
  (корень 2.25), поэтому архив побайтово одинаков между прогонами. Значения,
  не проходящие проверку своего типа (в наборе даты заменены словом
  «Anonymized»), пишутся пустыми. Запись — без pydicom (`dicom_sc.py`), как и
  резервный ридер; строгое чтение pydicom 3.0.1 проверяется тестом;
* **`<path_to_study>.png`** — та же картинка для быстрого просмотра без
  DICOM-просмотрщика;
* **`<исследование>/DXA_QC_report.sr.dcm` — отчёт DICOM SR** (ТЗ 2.6:
  «текстовое описание выявленных нарушений в формате DICOM SR»), один на
  исследование, вместе с DICOM-серией. Basic Text SR в том же
  StudyInstanceUID, серия `DXA QC report` (номер 9002): заключение по
  исследованию, по каждому уникальному кадру — область, нарушения словами
  ТЗ 2.3, измерения против порогов и балл, ссылки IMAGE на все файлы кадра
  (они же — в Current Requested Procedure Evidence Sequence). Статус
  `UNVERIFIED`: документ — подсказка, не заключение врача. Коды концептов —
  локальная схема `99DXAQC`. Запись без pydicom (`dicom_sr.py`),
  детерминированная; строгое чтение pydicom проверяется тестом. На обучающем
  наборе — 100 отчётов, по одному на исследование.

`--overlay-format dicom|png` оставляет одно из двух (отчёт SR — вместе с DICOM). На обучающем наборе
(499 файлов) архив с обоими представлениями — 135 МБ (только PNG — 51 МБ);
прогон без overlay — 7 с, с PNG — 20 с, с PNG и DICOM — 30 с (Linux-VM на
MacBook Air M2, 24 сентября); пиковая память с overlay — 242 МБ против 225 МБ
без него: архив пишется потоком, запись за записью. Время overlay в `time_of_processing` не входит.

На картинке — снимок, контур маски кости и ровно те измерения, по которым
принято решение: главная ось позвоночника против вертикали, нижняя полоса
для укладки, карта отклика top-hat при найденном артефакте, рамка поля
сканирования бедра с его длиной, прослеженный медиальный край и точка
выступа в окне малого вертела. Сработавшее правило — красным, в шапке —
итог и числа против порогов. Сбой отрисовки таблицу не трогает (причина —
в `overlay_errors.txt` внутри архива). Тепловая карта — отклик признака, а
не Grad-CAM: CNN в решении нет.

по фолдам осмыслен только для агрегатов: `quality_class` по всем
изображениям 0.65 ± 0.07. Полный разбор — `reports/day7_checkpoint.md` и
`reports/day9_rotation_overlay.md`, воспроизведение —
`python scripts/15_checkpoint_metrics.py`.

**С чем сравнивать.** При распространённости нарушений около 30% F1
тривиального ответа «всё — нарушение» не ноль: 0.45 по изображениям и
0.67 по исследованиям (нарушение есть в 50 исследованиях из 100). Честные
цифры решения — 0.60 и 0.74; парная разность с базой по изображениям —
**+0.14 [+0.05; +0.24]**, ДИ не касается нуля. До правила ротации бедро было ниже этой базы
(0.22 против 0.43), поэтому правило включено при F1 0.48 на своей метке —
обоснование в `reports/day8_multilabel.md`.

**Обучаемая голова не принята.** Логистическая регрессия на метку поверх
геометрии и эмбеддинга изображения, со вложенным выбором регуляризации и
порога, не обыгрывает правила ни на одной метке, а по агрегату даёт
+0.00 [−0.13; +0.12] (`scripts/16_multilabel_head.py`). Все проверенные
варианты на одной мере — слайд ТЗ 4 `reports/model_comparison/slide.png`
(`scripts/24_model_comparison.py`): классификатор по пикселям 0.48, гибрид
0.51, голова на геометрии 0.56, сервис 0.60, ResNet18-ротация из
экспериментальной ветки 0.63 (разность с сервисом +0.03 [−0.04; +0.10]),
ротация в точке точного локализатора вертела v2 0.56 (разность с сервисом
−0.04 [−0.12; +0.04], не включена — п. 8 «Ограничений»).

**Локализация ключевой точки (ТЗ 8.4, «расстояние между ключевыми
точками»).** Единственная ключевая точка, которую ставит сервис, — малый
вертел на overlay бедра. Расстояние от неё до точки врача на 58 кадрах,
где врач отметил вертел: медиана **9.0 мм**, p90 25.2 мм, в пределах 5 мм —
26%. Правило ротации меряет профиль края в окне вокруг этой точки, так что
промах точки — главная причина его ошибок (п. 8). Экспериментальный
локализатор v2 (OOF): медиана 2.5 мм, p90 18.8 мм, в пределах 5 мм — 84%;
в сервис не включён. Таблица — `reports/model_comparison/localization.csv`.

Определение анатомической области работает без разметки, по геометрии
кадра: **0 расхождений с просмотренным глазами эталоном на 252 кадрах**
(99 позвоночников, 79 левых бёдер, 74 правых).

* Разбиение на фолды зафиксировано (`reports/split.csv`), единица —
  исследование; повторный запуск с тем же seed даёт побайтово тот же файл.
* Версии зависимостей закреплены жёстко (`requirements.txt`, ТЗ 3.2).
* Выходной xlsx пишется детерминированно: фиксированы даты записей zip
  и свойства документа (openpyxl при сохранении перезаписывает
  `dcterms:modified` текущим временем — это исправляется при
  перепаковке). Два прогона различаются только колонкой
  `time_of_processing`, которую требует ТЗ 2.5; всё остальное
  совпадает — проверка `python scripts/verify_day6_pipeline.py`.
* Решения не зависят от архитектуры: образ, собранный под arm64 (Mac M2)
  и под amd64 (машина проверки, эмуляция), дал на обучающем наборе
  одинаковые таблицы — все 500 строк, область, класс, тип нарушения и
  статус совпадают.
* Стресс-тест: `python scripts/18_stress_test.py` — пустые, текстовые,
  обрезанные, цветные, сжатые без декодера, 1×1 и однотонные файлы,
  кадр 2048×2048, 29 копий одного кадра, кириллица и пробелы в путях,
  пустой архив; реальные кадры, перепакованные в MONOCHROME1, 16 бит и
  Explicit VR Big Endian. Ни одного вылета, строка на каждый файл,
  перепаковки не меняют ни одного решения; самое долгое исследование —
  0.6 с (кадр 2048×2048). Корпус можно прогнать и через контейнер
  (`--make-only`). Итог — `reports/stress/summary.json`.
* Тесты: `python run_tests.py` (без pytest) или
  `python -m pytest tests -q`. Обе ветви ридера — со встроенным разбором и
  с pydicom — проверяются отдельно: несколько ошибок за спринт были видны
  только в одной из них.
* Предупреждения pydicom не идут в stderr: они собираются в колонку
  `warnings` того изображения, к которому относятся. На обучающем наборе
  это сообщения «Invalid value for VR UI» в **488 файлах из 499** — в UID
  организатора компоненты начинаются с нуля, что стандарт запрещает. Файлы
  при этом читаются, а встроенный ридер принимает их молча. Это свойство
  всего набора, а не отдельных файлов, и одна из причин, по которым у
  решения есть собственный ридер, не зависящий от строгости чужой
  библиотеки.

# Ограничения

Раздел важнее метрик: он перечисляет то, где решение расходится с
буквальным текстом ТЗ или с экспертной разметкой, и почему.

## 1. Реализована половина критерия укладки позвоночника

Формулировка ТЗ 2.3.1 — конъюнкция: «в кадр не попали верхние края
подвздошных костей **и/или** половина тела Th12». Из маски проверяема
только первая половина. Признак из плана («касание маской нижнего края
кадра») оказался **вырожденным**: маска касается нижнего и верхнего края у
всех 99 исследований, у нарушений и у нормы одинаково.

Работает другое: плотность структур сбоку от позвоночника в нижней трети
кадра. Зазор между классами четырёхкратный (0.018 против 0.075),
специфичность 1.000. Два позитива из шести правило не ловит — у них гребни
в кадре, нарушена вторая половина критерия. Шесть признаков верха кадра их
не отделяют; на двух примерах правило не строится.

24 сентября проверена и анатомическая мера — сколько миллиметров кадра
выше гребней подвздошных костей. Длина скана у обоих позитивов обычная
(193 и 192 мм при медиане нормы 190 мм), по расстоянию до гребней они
13–33-й и 64–79-й среди 93 негативов в зависимости от порога — внутри
распределения нормы (`scripts/23_tz_criteria.py`,
`reports/tz_criteria/`). Надёжный путь — определение уровней позвонков
(L5…L1 по межпозвонковым щелям), для него нужна разметка уровней на
40–60 снимках; проверять его всё равно пришлось бы на тех же двух
позитивах. Это направление развития, а не правило до заморозки.

## 2. Порог наклона оси — 4.5°, а не буквальные 5°

Величина угла зависит от способа оценки: на одной маске хорда четвертей,
линия построчных центроидов и главная ось дают систематически разные
модули. Выбрана главная ось как самая устойчивая оценка, порог
откалиброван по F1: 4.5° даёт чувствительность 0.70 и специфичность 0.88,
буквальные 5° — 0.60 и 0.90.

Поверхность F1 по порогу плоская (3.3°–4.7° дают 0.46–0.50), и 4.5° —
её вершина на тех же данных. Если выбирать порог на четырёх фолдах, он
гуляет от 3.3° до 4.7°, а F1 на отложенных фолдах — **0.35**
[0.18; 0.52]. Это и есть ожидание на закрытом наборе.

## 3. Правило оси конфликтует с анатомией при сколиозе

Из 20 позвоночников с находкой вне перечня 2.3 (в основном сколиоз)
нарушением оси эксперт пометил **ровно один**: отклонение оси при сколиозе
он считает анатомией, а не ошибкой укладки. Шесть из десяти ложных
срабатываний правила — такие случаи. Без них AUC 0.933 против 0.878; это
не метрика решения, а адрес потолка.

Отсюда флаг `OUT_OF_SCOPE_FINDING`: находки вне перечня 2.3 попадают в
`violation_type` отдельной пометкой, но **не влияют на `quality_class`**.
Влияние дало бы 14 ложных срабатываний против одного совпадения с
экспертом.

Разбор ошибок 24 сентября это подтвердил: в разметке 14 позвоночников с
комментарием «сколиоз», метка оси у всех 14 — норма; 4 из 11 ложных
срабатываний конвейера — они. Признаки кривизны сколиоз от наклона не
отделяют (`reports/day12_errors_rules.md`).

## 4. Детектор артефактов обучен на 17 позитивах

F1 0.71, ДИ 95% [0.53, 0.86]. Конструкция признака (диаметр ядра ×
перцентиль отклика) перебиралась на тех же 99 изображениях, поэтому
out-of-fold здесь только обучение, но не выбор конструкции. Защита — в
физическом смысле признака (мелкие структуры высокого контраста вне кости)
и в ширине плато по параметрам. Обучен только на позвоночнике; на бедре не
применяется.

В зафиксированном сплите один фолд из пяти не содержит позитивов
артефактов, поэтому основная цифра — 20 повторов стратифицированной
проверки, а прогон по сплиту идёт рядом как воспроизводимая ссылка.

Что именно он ловит. На 9 из 12 верных срабатываний максимум отклика
лежит на рёбрах в верхней части кадра, а не на металле. Это совпадает с
разметкой: столбец эксперта — «посторонние предметы, выраженные
артефакты **или наложения**», и кадры с рёбрами размечены как нарушение
в 44% случаев против 8% у остальных. Поэтому рёбра из поиска не
исключаются (F1 упал бы до 0.26). Металлических предметов в наборе
единицы: признак top-hat на них рассчитан, но качество на металле не
измерено. Разбор — `reports/day11_errors_artifact.md`.

## 5. Порог охвата области интереса — 133 мм, а не 150 мм

Признак из плана («отступы bbox кости до краёв кадра против порогов 30 мм
сверху/снизу и 20 мм сбоку») **вырожден**: нижний отступ равен нулю у всех
150 изображений — диафиз выходит за нижний край кадра всегда.

Работает длина поля сканирования. Буквальное чтение ТЗ даёт минимум около
150 мм (9–10 см на проксимальный отдел плюс два отступа по 3 см), но
эксперт помечает нарушением только поля короче ~133 мм. Порог 133 мм стоит
в середине плато 125.4–139.8 мм, на котором решение не меняется.

Плато держится на двух позитивах одного фолда (124.2 и 125.4 мм), а
на 124.2 мм лежат ещё два негатива: длина поля принимает дискретные
значения протокола. Без этого фолда в обучении порог уходит на 123.9 мм,
и при честном выборе порога F1 — **0.50** [0.00; 0.82].

## 6. Боковое правило 20 мм из ТЗ на этих данных опровергается

Боковой отступ до границы области сканирования имеет медиану 8.4 мм.
Буквальное правило «< 20 мм» пометило бы нарушением 138 снимков из 150
(F1 0.04, специфичность 0.056), причём **связь обратная** — ROC-AUC 0.174:
у позитивов боковой отступ больше, чем у нормы. Правило не реализовано
сознательно: метрики считаются по разметке эксперта, а эксперт на этих
данных 2 см сбоку не требует. Отступ измеряется и показывается на overlay
бедра серой справочной строкой (`lateral margin … mm (TZ 20 mm, info
only)`), на `quality_class` и `violation_type` он не влияет.
Воспроизведение — `scripts/23_tz_criteria.py`.

## 7. Два позитива охвата из семи не ловятся

Поля 141.0 и 156.6 мм. Первое совпадает со значением сразу у нескольких
негативов — по длине скана эти случаи неразличимы в принципе. Боковой
отступ у них 10.9 и 7.3 мм при медиане 8.4 мм у негативов, то есть боковым
правилом они тоже не отделяются.

## 8. Правило ротации бедра — самое слабое, и включено сознательно

Самый крупный класс бедра — 36 позитивов из 41. Из геометрии маски он не
строится (угол диафиза: F1 0.42 при специфичности 0.62). 80 кадров
разметил врач (четыре анатомические точки на каждом): связь между
малым вертелом и ротацией **есть, но U-образная** — нарушению отвечают оба
края, вертел чётко видим (69% нарушений) и не видим вовсе (59%), а норме
середина, «еле виден» (10%). Держится во всех пяти фолдах. Видимость,
оценённая врачом, — не вход конвейера, поэтому правило строится на
автоматическом измерении.

**Что в конвейере.** Медиальный край бедра прослеживается от диафиза
вверх, в окне ниже шейки ищется выступ малого вертела. Решение — два
хвоста по одному признаку: нарушение, если выступ меньше нижней границы
или больше верхней, — прямое следствие U-образной связи. Признак выбран
из четырёх тем же правилом, что и во вложенной проверке (максимум F1 при
специфичности ≥ 0.75 на пяти фолдах): высота локального выступа
`bump_mm`, норма [−0.19; 0.66] мм. Выбор и границы заморожены
`scripts/17_fit_rotation_rule.py` в `models/rotation_profile_v1.json`;
значения признака в конвейере совпадают с таблицей, на которой подогнаны
границы, до 6·10⁻¹⁵ на всех 150 кадрах.

**Качество.** Вложенная проверка всей процедуры: F1 **0.48** [0.34; 0.61],
специфичность 0.75 (20 TP / 28 FP / 16 FN). Это ниже планки 0.49,
поставленной на метку заранее, но решает агрегат: без правила
`quality_class` бедра — 0.22, ниже тривиального «всё — нарушение» (0.43),
с правилом — 0.53; по всем изображениям 0.50 → 0.60, по исследованиям
0.65 → 0.74. Разность с правилами без ротации +0.09 [−0.01; +0.20] —
граница ДИ касается нуля.

Оговорки. Это четвёртый подход к ротации на тех же 150 снимках (дни 5–8):
вложенность защищает от выбора признака и границ, но не от выбора самого
подхода. Специфичность бедра падает с 1.000 до 0.76 — лишний просмотр
примерно каждого четвёртого нормального снимка. В признаке на обучении
(`bump_mm`) и во вложенной проверке (в четырёх фолдах из пяти —
`profile_contrast`) выбор между двумя лучшими признаками — монетка: 0.506
против 0.500. Если край не прослеживается, правило отказывается и нарушения
не ставит (1 кадр из 150), причина — в диагностике.

**Где ошибается (разбор 24 сентября).** Главный источник ошибок —
локализация малого вертела, а не границы. У 11 из 15 пропусков вертел
врачу хорошо виден, но окно поиска его не накрывает: якорь стоит на
гладком диафизе ниже, выступ около нуля. По точкам врача якорь
промахивается больше чем на 5 мм у 10 из 12 размеченных пропусков — и у
всех 11 размеченных верных срабатываний. Значит, и верные решения правило
получает не прямым измерением вертела, а признаком, который с ротацией
коррелирует на этих данных; на закрытом наборе это главный риск.
Добавка угла диафиза и согласование двух бёдер исследования вложенно не
помогают (`reports/day12_errors_rules.md`).

**Точный локализатор вертела проверен и не включён (24–25 сентября).**
Локализатор малого вертела проверен отдельным экспериментом на 58 точках,
которые поставил врач. Средний шаблон нормированных патчей 18×18 мм
искался вдоль медиального края; при OOF-проверке медиана ошибки снизилась
с 9.04 до 2.47 мм, доля попаданий в 5 мм выросла с 25.9% до 84.5%. Однако
правило ротации в найденной точке вложенно (двойной кросс-фиттинг
локализатора) дало F1 0.427 [0.27; 0.57], специфичность 0.798
(16 TP / 23 FP / 20 FN / 91 TN), а `quality_class` бедра — F1 0.444.
Пороги включения 0.53 и 0.527 были закоммичены до запуска проверки и не
пройдены, поэтому версия v2 не включена: сервис продолжает использовать
`rotation_profile_v1.json`. Точный анатомический ориентир не дал
устойчивого разделяющего признака на малом и смещённом наборе. Следующий
шаг — классификатор на области вокруг найденной точки (ResNet18 на
области вокруг кандидата вертела уже дал 0.50 вложенно, но в образ пришлось
бы добавить torch) — после заморозки. Отчёт —
`reports/day12_rotation_localizer.md`, воспроизведение — скрипты `20`–`22`.

**Спринт 26 сентября.** По критерию, записанному до запуска, проверены ещё четыре варианта ротации (логистическая регрессия на признаках в точке v2, профиле v1, геометрии маски и втором бедре: F1 0.44–0.47) и четыре варианта наклона оси с учётом сколиоза (изгиб осевой линии, наклон таза: F1 0.28–0.36 против 0.35). Ни один не прошёл, сервис не менялся. Отчёт — `reports/f1_sprint/README.md`.

Подробности — `reports/day6_rotation_landmarks.md`,
`reports/day6_rotation_human_profile.md`, `reports/day9_rotation_overlay.md`.
Разметка лежит в `annotations/femur_points_human.csv`
(`eligible_for_training=True`).

## 9. Масштаб изображения восстанавливается косвенно

`PixelSpacing` (0028,0030) и `ImagerPixelSpacing` (0018,1164) отсутствуют
**во всех файлах набора**. Единственный источник — `Exposed Area`
(0040,0303), но он описывает поле сканирования, а сохранённое изображение
— вырезку из него, поэтому оценка по нему завышена тем сильнее, чем сильнее
обрезан кадр (до 9.7% на обучающем наборе, 8.5% на отложенном).

Порядок источников: `PixelSpacing` → `ImagerPixelSpacing` → `Exposed Area`
→ паспортные 0.6 мм/пиксель (GE Lunar Prodigy Advance). Паспортом
ограничивается **только** оценка из `Exposed Area` — она заведомо оценка
сверху; достоверные теги принимаются как есть, иначе аппарат с пикселем
0.8 мм получил бы 0.6, длина поля вышла бы на четверть короче настоящей и
правило охвата начало бы штамповать ложные срабатывания.

Паспортное значение привязано к аппарату: в наборе 499 файлов из 499 —
GE Lunar Prodigy Advance. Если попадётся другой аппарат и достоверного
тега не будет, замечание об этом идёт в диагностику, а сводка в конце
прогона печатает распределение источников масштаба и список аппаратов.
Порог правила охвата калиброван (133 мм при плато 125.4–139.8), поэтому
остаточная ошибка масштаба в несколько процентов решения не меняет.

## 10. Ключ исследования — имя каталога, а не тег

`StudyInstanceUID` (0020,000D) внутри файлов принадлежит другой серии
идентификаторов и с `разметка.xlsx` не пересекается вообще, тогда как имя
каталога верхнего уровня совпадает с ней 100 раз из 100. Тег при этом
пишется в колонку `study_uid`, как требует ТЗ 2.5. Вопрос задан
организатору (п. 3 в `reports/questions_to_organizer.md`).

Отсюда зависимость от уровня каталога: роутер считает, что позвоночник в
исследовании один, и если указать каталог уровнем выше, все исследования
слились бы в одно. Поэтому обёртки снимаются автоматически: пока на уровне
один подкаталог, нет файлов DICOM, а файлов под ним больше 50 (самое
большое исследование набора — 29 файлов), корень опускается ниже.
`НД_для_обучения/` и `НД_для_обучения.zip` дают по всем 499 снимкам те
же строки, что и `Исследования/`, плюс строку `Failure` на лежащий рядом
`разметка.xlsx` — как на любой не-DICOM файл. Если «исследование» всё же содержит больше трёх
уникальных кадров (ТЗ 2.4), прогон печатает предупреждение.

## 11. Разметка организатора — на уровне «исследование × область»

разметки анатомических структур проверяется косвенно — через геометрию
маски, а не сравнением с эталонными контурами.

Три изображения из 499 (два исследования) организатором не размечены —

## 14. Видимость большого вертела, шейки и седалищной кости отдельно не проверяется

ТЗ 2.3.2 (рис. 4): при правильном позиционировании видны большой вертел,
шейка и седалищная кость. В разметке организатора позиционирование и
ротация — одна колонка, её закрывает правило ротации (п. 8). Отдельное
правило видимости проверено по оценке врача на 80 кадрах
(`annotations/femur_points_human.csv`) и не ставится:

| ориентир не виден (оценка врача) | норма | нарушение по разметке |
|---|---|---|
| седалищная кость | 10 | 8 |
| шейка | 0 | 0 (видна всегда) |
| большой вертел | 1 | 5 |

Отсутствие седалищной кости эксперт организатора нарушением не считает:
правило «не видна — нарушение» дало бы 10 ложных срабатываний на 8
верных. Большой вертел не виден на шести кадрах, из пяти нарушений три
уже ловит правило ротации; оставшиеся два боковой отступ не выделяет
(медиана 7.8 мм против 8.4 мм у кадров с видимым вертелом). Выигрыш — не
больше двух кадров без способа их найти. Воспроизведение —
`scripts/23_tz_criteria.py`, `reports/tz_criteria/`.
